## GC correction implementation changes (22/04/2026)

- **Bug discovered**: GC correction was being applied to non-GC-correctable features (`fsd`, `length`, `edm`, `eedm`, `iedm`, `cposedm`, `eoedm`, `ext_poem_prem`, `poem_prem`) in the old `cfdna_model.py`. The `gc_correct_features` allowlist existed on the class but was never checked inside `cv_svm()` — correction ran on any feature when `gc_correction=True`.
- **Mismatched dimensions**: for those smaller features (fewer columns than 561,414), `_gc_correct` silently used the first N rows of `gc_content_per_region.csv` as the GC values, which have no relationship to those feature columns. Results were nonsensical.
- **Affected result files deleted**: all `_gc_` run folders/CSVs from `svm_by_feature/` that contained GC correction applied to non-correctable features.
- **Speed issue**: the new `gen_cfdna_model.py` (`_fit_gc_correction`) refits LOWESS on every training split (~100 folds × ~413 samples = ~41,300 LOWESS calls on 561k points each), causing ~1 day runtime. Delta=gc_range/500 anchor points was added to speed up each individual LOWESS call but the per-fold refitting loop remains the bottleneck.
- **delta parameter**: `gen_matrix_processor.py` uses `delta = gc_range / 500.0` (vs `200.0` in the old `modelling/modules/matrix_processor.py`) to reduce interpolation evaluations per LOWESS call.
